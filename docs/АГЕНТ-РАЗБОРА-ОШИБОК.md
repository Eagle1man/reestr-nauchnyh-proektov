# Агент разбора ошибок и самосовершенствование разработки

Проработка идеи: в проекте появляется агент, который **постоянно разбирает
ошибки**, предлагает и проверяет исправления, а найденное знание не теряется
между запусками. Документ отвечает на три вопроса: что уже есть, что
добавляем и чего сознательно не делаем.

Дата проработки: 31.10.2026.

---

## 1. Что уже есть — на что опираемся

Идея не начинается с нуля: в проекте уже есть три из пяти нужных частей.

| Часть | Где | Что даёт |
|---|---|---|
| Сбор ошибок сервера | `backend/app/errors.py` — круг на 200 записей в памяти, `GET /api/admin/diagnostics` | код обращения, тип, сообщение, путь, логин |
| Сбор ошибок браузера | `frontend/src/components/ErrorReportButton.tsx` — отчёт собирается на машине пользователя | то, что видел браузер и что делал человек |
| Журнал действий | неизменяемый аудит (FR-23) | кто, что и когда изменил — контекст для разбора |
| Комплект проверок | 414 тестов бэкенда, `smoke.py`, `check_ui.py`, `tsc` | чем проверять исправление |
| Память отдела | `D:\itотдел\obsidian-mind`, `recall`/`remember` | куда писать урок, чтобы он пережил сессию |

**Чего не хватает:** ошибки живут в памяти и теряются при перезапуске; у них
нет отпечатка (одна и та же ошибка от 50 пользователей — это 50 строк, а не
одна проблема); нет автоматического перехода «ошибка → причина → исправление →
проверка»; нет измерения, стало ли лучше.

---

## 2. Ограничения, которые определяют архитектуру

Это не пожелания, а требования самого проекта и отдела:

1. **SEC-05 / N-03.** Наружу не уходит ничего: ни ошибки, ни содержимое базы,
   ни персональные данные. Значит агент не может быть облачным сервисом,
   который «сам смотрит прод» — он работает на машине разработчика с тем, что
   человек ему принёс.
2. **Публикацию делает человек.** Агент не пушит в основную ветку и не
   выкатывает на сервер: только ветка, только через проверки, только с
   подтверждением.
3. **Формулировка ошибок не содержит персональных данных.** Сейчас в записи
   есть `user` (логин). Для машинного разбора достаточно роли: логин не нужен.
4. **Расход.** Порог отдела — 250 тыс. токенов на ход, иначе сессия
   квадратична. Агент обязан работать по артефакту (отчёт), а не по проекту.

## 3. Архитектура: пять частей

### 3.1. Сбор и отпечаток (fingerprint)

Каждая ошибка получает отпечаток: хэш от `тип + нормализованное сообщение +
место в коде + версия сборки`. Нормализация убирает то, что делает записи
разными при одной причине: числа, идентификаторы, пути, адреса.

```
"Ошибка при сохранении проекта 3f2a… на /api/projects/3f2a…"
→ "Ошибка при сохранении проекта <id> на /api/projects/<id>"
```

Отпечаток превращает поток в **список проблем**: 200 записей → 3–7 отпечатков.
Это первое, без чего агент бесполезен: разбирать 200 строк по одной дороже,
чем исправить причину.

### 3.2. Хранилище ошибок

Варианты (решение нужно от заказчика, см. раздел 7):

- **A. Как сейчас** — память процесса, отчёт забирает человек. Ничего не
  меняется, но история не копится, и «часто ли это повторяется» не узнать.
- **B. Локальная таблица** `error_events` в той же SQLite: отпечаток, тип,
  сообщение, путь, роль, версия сборки, счётчик, первое и последнее
  появление. Наружу не уходит, срок хранения — 90 дней, логин не пишем.
- **C. Файл-журнал** рядом с базой — то же, что B, но без схемы.

Рекомендация: **B**. Это 1 таблица, 1 миграция и один запрос на вставку;
данные остаются внутри установки, а появляется история, без которой нет
измерения «повторяется или нет».

### 3.3. Разбор: агент по отчёту

Вход — выгрузка (`diagnostics` + экспорт отпечатков), а не доступ к серверу.
Выход — **карточка разбора** на каждый отпечаток:

```
ОТПЕЧАТОК: a41f…  (12 появлений, 4 пользователя, 3 дня)
СИМПТОМ:   Ошибка 500 при сохранении проекта, шаг «Результаты»
ГИПОТЕЗА:  в PATCH /api/projects/{id} не проверяется пустой список программ
ДОКАЗАТЕЛЬСТВО: backend/app/api/projects.py:318 — .program_ids[0] без проверки длины
ИСПРАВЛЕНИЕ: 2 строки + тест на пустой список
ПРОВЕРКА:  pytest backend/tests -q → 414 passed (+1 новый)
РИСК:      изменение поведения API при пустом списке — нужно решение
```

Правила карточки: **гипотеза без доказательства не принимается** — нужна
строка в коде; **без теста исправление не считается**; **риск описывается
отдельно**, потому что не всякая правка безопасна.

### 3.4. Проверка и выпуск

Порядок жёсткий, как в отделе:

1. ветка `fix/<отпечаток>` от текущей;
2. правка + регрессионный тест, который **падает до правки** и проходит после;
3. полный набор: `pytest` (414), `tsc --noEmit`, `smoke.py`, `check_ui.py`;
4. гейт критики в отдельном окне (как принято в отделе);
5. человек смотрит диф и решает;
6. только после этого — слияние. Публикация на сервер — человек.

### 3.5. Самосовершенствование: три контура

Слово «самосовершенствуется» имеет смысл только если оно измеримо. Три
контура, каждый замыкается сам:

**Контур 1 — знание.** После каждого разбора в память отдела пишется урок с
охватом `project`: «такая-то ошибка была из-за такого-то класса причин, чем
проверяется». Урок подтягивается при следующем `checkout` через `recall` —
иначе он не работает (в отделе был замер: сессия без упоминания памяти
делает ноль обращений).

**Контур 2 — устойчивость.** Исправленная ошибка становится тестом. Раз в
неделю набор проверок прогоняется на **синтетически испорченной** копии кода
(внесение дефекта в модуль и проверка, что тесты его ловят). Это то, чем
занимается `SWE-smith`: без такого прогона «мы всё исправили» — утверждение
без доказательства.

**Контур 3 — качество самого агента.** Каждая карточка разбора оценивается
человеком: верна ли причина, принята ли правка. Доля принятых карточек —
показатель агента; если падает, меняется промпт, а не проект.

Вывод по чужим репозиториям: **готового решения «поставь и работает» под наши
ограничения нет.** Все перечисленные либо требуют отправки данных наружу
(Sentry, Langfuse), либо рассчитаны на Kubernetes (holmesgpt, k8sgpt,
chaos-mesh), либо решают только одну часть (SWE-agent — патчи, SWE-smith —
замер). Поэтому разумно **взять схемы, а не зависимости**: отпечатки и
группировку — как в Sentry, карточку разбора — как у holmesgpt, замер — как у
SWE-bench.

## 5. Минимальный объём (MVP) — 3 шага

Не «агент, который всё делает», а то, что даёт пользу на этой неделе:

1. **Отпечаток и группировка** в `errors.py` + поле в `diagnostics`:
   `fingerprint`, `count`, `first_seen`, `last_seen`. Полдня работы, ноль
   изменений схемы.
2. **Команда `node agent/errors.mjs --from <файл отчёта>`**: группирует,
   печатает карточки-заготовки (симптом, место, гипотеза без доказательства
   помечена как гипотеза). Логика без LLM для того, что видно по стеку.
3. **Регламент** в `docs/`: кто и когда разбирает, что считается закрытым,
   какие метрики смотрим. Без регламента агент через месяц перестают читать.

Дальше — по результатам: если карточки реально экономят время, добавляется
LLM-разбор и контур 2.

## 6. Метрики (иначе «стало лучше» — не факт)

| Показатель | Как считается | Цель |
|---|---|---|
| Время до разбора (MTTR) | от первого появления отпечатка до закрытия | ≤ 5 рабочих дней |
| Доля повторных | отпечатки, вернувшиеся после закрытия | ≤ 10% |
| Доля принятых карточек | принято человеком / предложено агентом | ≥ 60% |
| Прирост защиты | регрессионных тестов добавлено | ≥ 1 на исправление |
| Побеги | дефекты, найденные пользователем после исправления | 0 критических |

## 7. Решение, которое нужно от заказчика

**Хранить ли ошибки на диске локально** (вариант B) вместо памяти процесса.

- «За»: появляется история и счётчики повторов, без них измерение невозможно.
- «Против»: в базе появляются сведения о сбоях, которые сейчас не сохраняются
  вообще. Логин не пишем, но роль и путь — это данные о работе пользователей.
- Компромисс: хранить 90 дней, без логина и без текстов пользователя, только
  тип, отпечаток, место и роль. Такой набор персональными данными не является.

Без этого решения MVP шага 1 делается в памяти: отпечатки и счётчики живут
до перезапуска, история не копится.

## 8. Чего не делаем и почему

- **Агент в проде, который сам смотрит ошибки** — нарушает SEC-05 и N-03:
  данные ушли бы наружу. Разбор идёт по выгрузке на машине разработчика.
- **Автоматическое слияние правок** — противоречит правилу «публикует
  человек» и четырёхглазой проверке.
- **Свой LLM внутри установки** — для 6–50 пользователей это дороже, чем
  польза; сначала измеряем, сколько даёт разбор без модели.
- **Chaos engineering** — у проекта одна машина и одна база; вносить сбои
  в неё полезнее тестами, чем хаосом.
